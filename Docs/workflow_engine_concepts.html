Naming anti-patterns

Definition vs. Instance - the most fundamental distinction

WorkflowDefinition
Also called: Blueprint, Template, Schema, Workflow (bad - see below)
The static, versioned description of what a workflow does. Contains nodes, edges, initial state schema, and policies. Never mutated at runtime. One definition can produce thousands of instances simultaneously. Stored in SQL as a versioned document.
Prefer: DefinitionAlso fine: BlueprintAvoid: "Workflow" alone
WorkflowInstance
Also called: Execution, Run, WorkflowRun
One live execution of a definition. Has its own identity, state, status, and pointers. Created when a trigger fires. Multiple instances of the same definition can run concurrently. Stored persistently so it survives process restarts.
Prefer: InstanceAlso fine: Execution, RunAvoid: "Workflow" (same name as definition)
The core naming trap: Calling both the definition and the running execution "Workflow" is the #1 source of confusion in workflow engine codebases. You will end up with WorkflowId that could mean either the definition PK or the instance PK. Separate them from day one: DefinitionId and InstanceId are unambiguous.
ConfusedWorkflow.Id - is this the template or the run?
workflow.Start(workflowId) - starting what exactly?
GetWorkflow(id) - definition or instance?
Cleardefinition.Id / instance.InstanceId - unambiguous
engine.StartAsync(definition, event) - obvious
store.GetInstance(id) / store.GetDefinition(id)

Node / Activity - the unit of work

Node (in definitions) / Activity (in code)
Also called: Step, Task, Action, Unit, Element
The atomic unit of a workflow graph. In the definition JSON it's a "node" (graph terminology). In code the implementation is an "activity" or "executor". These two words refer to the same concept from different angles - the graph slot vs. the behaviour that fills it.
Prefer: Node (graph), Activity (behaviour)Also fine: Step (for linear engines)Avoid: Task (collides with System.Threading.Tasks.Task)
NodeDefinition
The static slot in the blueprint
Describes a single node: its unique ID within the definition, the TypeKey used to resolve its executor via DI, its configuration, and optional per-node retry/timeout overrides. The NodeId must be stable across definition versions so the execution log stays meaningful.
TypeKey / ActivityType
The discriminator that connects a node slot to its executor
A string constant like "LogicGate", "DeviceTrigger", "SendCommand". Used as the key in DI (Keyed Services in .NET) to resolve the correct executor at runtime. This is what makes the engine "blind" - it doesn't know what a LogicGate does, only that it should ask DI for one.
Prefer: TypeKey or ActivityTypeAvoid: NodeType (too generic, collides with graph node types)
Naming convention for TypeKeys: Use PascalCase nouns describing what the node is, not what it does. HttpRequest not CallHttp. DeviceTrigger not WatchDevice. LogicGate not CheckCondition. Nouns compose better in a visual designer.

Edge / Connection - the wiring between nodes

EdgeDefinition / Connection
Also called: Link, Transition, Arrow, Wire
Defines how one node's output connects to another node's input. An edge is directional: (SourceNodeId, SourcePort) → (TargetNodeId, TargetPort). Multiple edges can originate from a single port (fan-out). Multiple edges can point at the same target node (fan-in - requires a gate).
Prefer: Edge (graph theory), Connection (visual designer)Also fine: Link, WireAvoid: Transition (implies state machine, different semantics)
Edge vs. Transition: A transition (state machine term) changes the state of a single object. An edge (graph term) routes execution from one node to another. In a workflow engine the distinction matters: multiple edges can be active simultaneously (parallel branches), but a state machine can only be in one state at a time. Use "edge" to avoid inheriting state machine assumptions.

Port / Outcome - named exits from a node

Port / Outcome / OutputPort
Also called: Exit, Handle, Output, Connector
A named exit point on a node. When a node finishes executing it activates exactly one port. Edges leaving the node are attached to specific ports. Standard ports: "done", "true", "false", "timeout", "error". Custom ports: "high", "low", "offline". The activated port name determines which edges are followed.
Prefer: Port (engineering), Outcome (business language)Also fine: OutputHandle, ExitAvoid: Result (too generic, conflicts with return values)
ActivatedPort / ActivatedOutcome
The port name returned by an executor after it runs
The string name of the port the executor decided to activate. Returned inside the NodeResult. The engine uses this to look up outbound edges. If no edge matches the activated port, execution on that branch ends (terminal). This is the primary navigation mechanism - not return codes, not booleans.
Standard port vocabulary: Establish a consistent set of reserved port names across all node types. done - completed successfully with one outcome. true/false - binary condition. error - handled failure (routes to error handler node). timeout - deadline exceeded. cancelled - externally cancelled. Custom ports for domain logic: online/offline, high/normal/low, approved/rejected.

Instance lifecycle - the status vocabulary

InstanceStatus
The coarse status of a workflow instance. Every status should be mutually exclusive and cover every possible state of the instance.
Pending - created, not yet started (queued by ConcurrencyPolicy)
Running - at least one pointer is actively executing
Suspended - all pointers are parked on bookmarks, none active
Completed - all pointers reached terminal nodes successfully
Failed - error policy exhausted, instance halted
Compensating - rolling back already-executed nodes
Cancelled - externally cancelled before completion
Avoid: "Waiting" (ambiguous - waiting for what?) Avoid: "Paused" (implies user intent, not system state)
Running vs. Suspended: An instance is Running even if some pointers are suspended - as long as at least one pointer is actively executing. It becomes Suspended only when every pointer is parked. This distinction matters for observability dashboards and concurrency policy checks.

Pointer / Token - tracking position in the graph

ExecutionPointer
Also called: Token (Petri net term), Cursor, ExecutionCursor, Thread
Tracks where execution currently is within a workflow instance. Each pointer has a current node, a status, and a retry count. An instance starts with one pointer. Fan-out creates additional pointers. Fan-in retires all but one. Think of it as a cursor moving through the graph.
Prefer: ExecutionPointer, TokenAvoid: Thread (collides with OS threads), Cursor (implies DB)
PointerStatus
Fine-grained status of a single pointer within an instance.
Active - currently executing or queued to execute
Suspended - parked on a bookmark, waiting for an event
Sleeping - parked on a delay timer specifically
WaitingForJoin - arrived at a fan-in gate, not yet the winner
Completed - reached a terminal node
Failed - error exhausted retries on this branch
Cancelled - externally cancelled
Why "Pointer" and not "Thread": A pointer is a logical concept - a position in a graph. A thread is an OS concept - a unit of CPU scheduling. Calling it a thread implies one OS thread per branch, which is wrong (branches share a thread pool). Pointer is the accurate term.

Context objects - what gets passed to executors

ExecutionContext
Also called: ActivityContext, NodeContext, StepContext
The object passed into a node executor when it runs. Contains everything the executor needs: the node's config, access to workflow state, the triggering event, DI services, logging, and a cancellation token. It is the executor's complete API - the executor should need nothing else.
Prefer: ExecutionContext, ActivityContextAvoid: WorkflowContext (too broad - which workflow?)
TriggerContext
Also called: TriggerEvent, InputEvent, InboundEvent
Carries the original event that started (or resumed) the workflow. Available on the ExecutionContext of the first node. Subsequent nodes access it from state if they need it. Separating TriggerContext from ExecutionContext is important: not every node execution has a live trigger event (middle nodes in a chain don't).
CompensationContext
Passed to a compensatable executor during rollback. Includes the node's original output so it can undo whatever it did (e.g. the device command ID to cancel, the record ID to delete).

Executor pattern - separating definition from behaviour

INodeExecutor / IActivityExecutor
Also called: IStepBody (WorkflowCore), IActivity (Elsa), Handler
The interface every node behaviour implements. Has a single method: ExecuteAsync(context) → NodeResult. Registered in DI with a TypeKey. The engine never knows what the executor does - it just calls it. This is the "Blind Executor" principle: the engine is a generic scheduler, not a domain expert.
Prefer: INodeExecutor, IActivityExecutorAvoid: IWorker (too generic), IHandler (collides with MediatR)
ICompensatableExecutor
Optional interface an executor can additionally implement. Adds CompensateAsync(CompensationContext). The engine calls this during rollback in reverse execution order. Only executors that make side effects (send commands, write records) need to implement this.
Blind Executor principle: The engine resolves executors by TypeKey via keyed DI. It passes in a context and receives a NodeResult. It does not know whether the executor is sending an HTTP request, evaluating an expression, or publishing to RabbitMQ. This is intentional - new node types are added without touching the engine.

Bookmark / Subscription - the suspend/resume primitive

Bookmark
Also called: Subscription, WaitHandle, Suspension, Continuation
A persisted record saying "instance X, pointer Y is parked, waiting for an event named Z. When that event arrives, resume execution at node N." The bookmark name is the lookup key. Bookmarks survive process restarts because they live in Redis/SQL. This is what turns an in-memory engine into a durable one.
Prefer: Bookmark (Elsa term, widely understood)Also fine: Subscription, ContinuationAvoid: WaitHandle (OS primitive), Pause (implies user action)
BookmarkName
The lookup key - must be deterministic and unique per event type
The string key used to find bookmarks when an event arrives. Should encode the event type and the specific entity being watched. Convention: "{eventType}:{entityId}" e.g. "device:7a3b:temperature", "approval:request:4f2c". Bookmarks are found by exact name match - the name IS the routing.
DelayedResume / SleepRecord
A special bookmark variant for timer-based waits. Stores the absolute resume timestamp. A background scheduler service polls for expired records and publishes synthetic resume events. Separating this from regular bookmarks allows different storage strategies (e.g. Redis sorted sets for efficient time-range queries).

Trigger vs. Signal - two very different concepts

Trigger
Starts a new instance
An event that causes the engine to create a new workflow instance. A trigger matches a TriggerNode in a definition. The RuntimeRegistry maintains a lookup from trigger keys (e.g. "device:7a3b:motion") to matching enabled definitions. One event can trigger multiple definitions simultaneously.
Signal / ResumeEvent
Resumes an existing suspended instance
An event that resumes a parked pointer by matching its bookmark name. The engine looks up bookmarks, not definitions. One event can resume multiple instances if multiple bookmarks share the same name. Signals do not create new instances.
Why this distinction is critical: The same physical event (e.g. a device temperature reading) can simultaneously be a trigger (start a new "high temperature alert" workflow) AND a signal (resume an existing "monitor this device" workflow that's waiting for a reading). The routing logic is completely different - triggers go through the Registry, signals go through the BookmarkStore. Conflating them is a common architectural mistake.
Conflated (wrong)"An event starts or resumes workflows" - one code path tries to do both, gets confused about whether to create or resume
Separated (right)Engine checks bookmarks first (resume path), then checks Registry (start path). Both can fire for the same event.

Correlation - routing events to the right instances

CorrelationId
Also called: TenantKey, EntityKey, RoutingKey
A business-meaningful string that groups related instances together and routes events to the right ones. In IoT: "device:7a3b". In approvals: "request:4f2c". Set at instance creation time, immutable thereafter. Used by ConcurrencyPolicy checks (e.g. "only one running instance per device") and by bookmark lookup (filter by correlationId for performance).
Prefer: CorrelationIdAvoid: SessionId (implies HTTP), GroupId (too vague)
CorrelationKey (on events)
The CorrelationId extracted from an incoming event. Used to find bookmarks and check concurrency. Should match the format used when the instance was created. In IoT: built from the device ID in the MQTT topic.
CorrelationId vs. WorkspaceId: CorrelationId identifies which entity this workflow is about (a specific device). WorkspaceId identifies which tenant owns it. They serve different purposes - don't merge them into one field.

Fan-out / Fork - splitting execution into parallel branches

Fan-out / Fork
Also called: Split, Parallel, Branch, Scatter
When one node activates a port that has multiple outbound edges, execution splits into multiple independent parallel branches. Each branch gets its own ExecutionPointer. Branches run concurrently on the thread pool. The source pointer is retired.
Prefer: Fan-out (clear direction), Fork (OS/Git metaphor)Avoid: Split (implies the data splits, not execution), Parallel (describes the result, not the action)
FanOutNode / ParallelNode
An explicit node type whose entire purpose is to fan-out. Distinct from implicit fan-out (any node with multiple edges on one port). An explicit FanOutNode makes the intent visible in the graph designer - you can see at a glance that this is an intentional split.

Fan-in / Join / Gate - merging parallel branches

Fan-in / Join
Also called: Merge, Synchronize, Barrier, Gather
A node that waits for all incoming parallel branches to complete before proceeding. The first branch to arrive parks itself. Subsequent branches also park. The last branch to arrive (the "winner") continues past the join node. All parked branches are then retired.
Prefer: Join (database/parallel term), Fan-inAvoid: Merge (implies combining data), Synchronize (OS term)
FanInGate / JoinGate / JoinBarrier
The persistence record that tracks branch arrivals. Fields: GateId (= joining node's NodeId), InstanceId, ExpectedBranches (set at fan-out time), ArrivedBranches (atomically incremented). The gate fires when Arrived == Expected. Using an atomic increment (Redis INCR) means no application-level locking is needed.
Prefer: FanInGate, JoinGateAvoid: Semaphore (OS term with different semantics), Lock
Gate vs. Barrier: A barrier (concurrency term) blocks all threads until all have arrived. A gate in a workflow engine is softer - branches park themselves and the last one through cleans up the others. The gate analogy is better: it opens when the last branch arrives, lets one through, closes behind it.

Branch vs. Pointer - a naming distinction worth making

Branch
A logical path through the graph
A conceptual term for one of several parallel paths of execution. Use "branch" in documentation, user-facing messages, and designer UI. It's the intuitive word - "this workflow has three branches running in parallel."
ExecutionPointer
The implementation tracking a branch
The actual data structure that implements a branch. Use "pointer" in code, database schemas, and engine internals. One pointer per branch. A branch is what the user sees; a pointer is how the engine tracks it. Don't mix these in the same layer.
UI / Docs language"This workflow has 2 branches running in parallel. Branch 1 is waiting for a sensor reading. Branch 2 is executing a command."
Code / Engine languageinstance.Pointers.Where(p => p.Status == Active) - two active pointers, one suspended, one executing.

State namespacing - avoiding key collisions

WorkflowState
The live memory of an instance. Contains two distinct namespaces that must never be merged into one dictionary.
NodeOutputs - keyed by NodeId
Also called: ActivityState, StepResults
Each node's output stored under its own NodeId key. state.NodeOutputs["check-temp-node"]. Never under a generic key like "lastOutput". This means any downstream node can read any upstream node's output without ambiguity, and parallel branches can't overwrite each other's results.
Prefer: NodeOutputs[nodeId]Avoid: state["output"] - first parallel branch to write wins, second loses
Variables - named workflow-level values
Business-meaningful named values defined in the definition schema. Typed (string, number, bool, object). Set by special AssignVariable nodes or via output mapping. Accessed by name across any node. These are the "parameters" of the workflow - things like thresholds, device IDs, escalation recipients.
Deep clone on write: Every write to NodeOutputs and Variables must deep-clone the value. This is the fix for the shallow copy bug. Two instances of the same definition must never share a reference to the same object. Use JsonElement (inherently immutable) or explicit deep-clone on assignment.

Variable vs. Output - two kinds of data

Output / NodeOutput
Data produced by a specific node execution. Namespaced under that node's ID. Immutable after the node completes. Read-only to downstream nodes. Examples: the parsed temperature value from a sensor reading node, the response body from an HTTP call node, the evaluation result from a logic gate node.
Variable / WorkflowVariable
A named, mutable value at workflow scope. Can be read and written by any node. Defined in the definition with a name and type. Used for values that need to accumulate or change across multiple steps - e.g. a counter, a running total, a flag set by one branch and read by another.
Use Output forThe result of what this specific node just did. Sensor reading, HTTP response, expression evaluation result, device command ID.
Use Variable forCross-cutting values that live for the whole workflow. Alert threshold, retry counter, accumulated device state, user-provided configuration.

Scope levels - where data lives

Definition scope
Static config baked into the definition. Immutable at runtime. Examples: node configs, thresholds defined at design time, policy settings. Deep-cloned into instance state at creation - never read directly from the definition during execution.
Instance scope
Lives for the lifetime of one instance. Variables and NodeOutputs. Serialised and persisted so it survives suspension and process restart. Shared across all pointers (branches) of the same instance - requires namespacing by nodeId to prevent cross-branch writes.
Node scope / Execution scope
Lives only for the duration of one node execution. The ExecutionContext itself. Local variables computed inside ExecuteAsync. The IServiceScope (DI). Discarded after ExecuteAsync returns. Never persisted.
Resume scope
Data carried by the resuming event - the payload of the bookmark match. Available via context.ResumePayload or injected into NodeOutputs under a reserved key. Only present when a node is resuming from a bookmark, not on first execution.

Error vs. Fault vs. Exception - three different things

Exception (code layer)
A .NET exception thrown by executor code. Caught by the engine's retry wrapper. Converted into a NodeError after retries are exhausted. Executors should only throw - never catch-and-swallow - so the engine can handle retry correctly.
NodeError (engine layer)
Also called: ExecutionError, NodeFailure
A structured record produced by the engine after retries are exhausted. Contains: message, attempt count, timestamp, nodeId. Written to the execution log. Used by HandleError to decide whether to route via error port, apply error policy, or compensate.
WorkflowFault (instance layer)
The terminal failure state of a whole instance. Set when the error policy is exhausted and the instance cannot continue. Different from an individual node's NodeError - a fault is instance-level, an error is node-level. An instance can have nodes that errored (and were handled) without the instance faulting.
Prefer: WorkflowFault for instance-level failuresAvoid: using "error" and "fault" interchangeably

Retry vs. Compensation - forward vs. backward recovery

Retry / RetryPolicy
Forward recovery: try the same operation again. Applied at the node level before the error is escalated. Policy fields: MaxRetries, BackoffMs (with exponential + jitter), RetryableExceptionTypes (only retry transient errors, not validation failures). Retry is transparent - the workflow doesn't know it happened.
Compensation / Rollback
Backward recovery: undo what already succeeded. Applied at the instance level when retry is exhausted and the workflow cannot continue forward. Walks the execution log in reverse, calling CompensateAsync on each completed node that implements ICompensatableExecutor. Think of it as the workflow's "undo stack."
Prefer: Compensation (saga pattern term)Avoid: Rollback (implies database transaction, different semantics)
Retry (forward)Node fails → wait → try again → succeed → continue. The workflow moves forward. Used for transient failures: network timeout, device temporarily offline.
Compensation (backward)Node fails → retries exhausted → undo node N-1, N-2, N-3 → instance marked Failed. Used when the operation is definitively broken.

Policy objects - named bundles of behaviour rules

RetryPolicy
Fields: MaxRetries, BackoffMs, UseExponentialBackoff, JitterMs, RetryableOn (exception type list). Defined at definition level with per-node overrides. Applied by ExecuteWithRetryAsync wrapper - never by the executor itself.
ErrorPolicy
Fields: OnExhausted (enum: Fail | Compensate | Skip | RouteToErrorPort). Applied after all retries fail. Skip is useful for non-critical branches in parallel workflows - let other branches continue.
ConcurrencyPolicy
Fields: Mode (AllowParallel | Queue | CancelPrevious | DropNew | Debounce), DebounceWindowMs. Applied in RuntimeRegistry before StartAsync is called. The only policy evaluated before instance creation.
TimeoutPolicy
Fields: NodeTimeoutMs (per-node deadline), InstanceTimeoutMs (whole-workflow deadline). Node timeout is enforced by CancellationTokenSource in the retry wrapper. Instance timeout is enforced by a background scheduler that publishes a synthetic cancel event.

Sub-workflow / Child - workflow composition

Sub-workflow / ChildWorkflow
Also called: Nested workflow, Workflow invocation, Call activity
A node that starts another workflow definition as a child instance and waits for it to complete. The parent pointer suspends on a bookmark. When the child completes, it resumes the parent and passes outputs back. The child is a full WorkflowInstance with its own state, pointers, and lifecycle - it just has ParentInstanceId set.
Prefer: SubWorkflow, ChildWorkflowAvoid: "nested workflow" (implies structural nesting, not invocation)
InputMapping / OutputMapping
Declarative rules on the SubWorkflow node config that describe how parent state maps to child Variables on start, and how child Variables map back to parent state on completion. Keeps the coupling between parent and child explicit and schema-validated.

Composite activity - a node that contains other nodes

CompositeActivity / ContainerNode
An activity that contains child nodes and manages their execution internally. Examples: Sequence (run children in order), Parallel (run children as fan-out), ForEach (run one child per item in a collection). Different from a sub-workflow: composite activities share the parent's instance state and run within the same instance. Sub-workflows are separate instances.
Composite activitySame instance. Same state. Same execution context. Children are graph nodes inside the composite. Designer shows them as expandable. Good for reusable patterns within one workflow.
Sub-workflowSeparate instance. Separate state. Separate lifecycle. Connects via bookmark. Good for reusable workflows that can also be triggered independently.

Registry vs. Store vs. Engine - three different roles

WorkflowRuntimeRegistry
In-memory index of enabled definitions, keyed by trigger patterns. Answers the question: "which definitions should run for this event?" Does NOT store instances. Does NOT execute anything. Just routing. Rebuilt from the definition store on startup and refreshed on change events.
WorkflowStore / IPersistenceStore
The persistence abstraction. Handles all reads and writes: instances, bookmarks, fan-in gates, delayed resumes, definitions. Implemented against SQL (definitions), Redis (bookmarks, gates), or both. The engine never writes to a database directly - only via the store interface.
WorkflowEngine
The orchestrator. Calls the Registry to find definitions, calls StartAsync/ResumeAsync to move instances forward, delegates to executors via DI, calls the Store to persist state. Registered as a Singleton - but never holds scoped services directly (captive dependency fix).
Separation of concerns: Registry knows what to run. Engine knows how to run it. Store knows how to persist it. Executors know what the node does. No class should own more than one of these responsibilities.

Naming anti-patterns - what to actively avoid

"Workflow" used for both definition and instance
The most common mistake. Results in WorkflowId being ambiguous, GetWorkflow() being meaningless, and every method signature being unclear. Always qualify: WorkflowDefinition vs. WorkflowInstance.
Avoid: Workflow, WorkflowId alone
"Task" for node/step
Collides with System.Threading.Tasks.Task in .NET. Every code reader will mentally parse it wrong. Use Node, Activity, or Step instead.
Avoid: Task, WorkflowTask
"Status" for both instance and pointer
Instance has a status (Running, Suspended, Completed). Each pointer has a status (Active, Suspended, Failed). Use InstanceStatus and PointerStatus as distinct types - not both named Status.
Global state dictionary with string keys
state["output"], state["result"], state["data"] - untyped, unscoped, collision-prone. When two parallel branches both write state["result"], one silently overwrites the other. Always namespace by nodeId.
Avoid: Dictionary<string, object> with generic keys
Conflating Trigger and Signal
Treating "start a new instance" and "resume an existing one" as the same code path. They use different lookups (Registry vs. BookmarkStore) and have different failure modes. Keep them as separate methods: StartAsync and ResumeAsync.
