# Post-merge review of the 19 Nov fixes

Every PR merged on 19 Nov 2026 to fix the findings of the [18 Nov review](2026-11-18.md) (epic #938) was read again, as it stands on `master`, from the three angles in [README §3](README.md): product, architecture and senior developer. Eight reviewers took one batch each; each finding was verified against the code before it was kept.

**84 PRs** across wbskt/Wbskt, Wbskt.Python, wbskt.dotnet, Wbskt.Arduino, Wbskt.Admin and the website. **77 findings:** 7 bugs, 48 should-fix, 22 nits.

- Every PR has a "Post-open review:" line. 62 are substantive and 22 are thin (a one-line "nothing found", or only checked a data block parses).
- The PRs' own reviews were almost all from the senior-developer angle. Few looked at the product angle, and none of the library reviews looked across the three SDKs, which is where most library findings are.
- 19 PRs did not fully do what their issue asked; the gap is listed with each.

## Bugs

- **A rollback to any commit before #1041 deploys but is reported as failed: the watcher reads only a status file the old script never writes** (wbskt/Wbskt#1041, senior). `deploy/scripts/deploy.sh:226-239 (detach_and_follow), :198-209 (sync_and_reexec)`  
  Production breaks after a release, and the operator follows the documented rollback ('Dispatch it by hand to redeploy or roll back to an older tag') to a sha older than 94f91e8. The rollback completes on the VM, but the watcher finds no status file and exits 1. deploy.yml goes red, opens or comments on 'Production deploy failed', and skips 'Move :latest'. In the middle of an incident the operator is told the rollback failed.  
  Fix: Use the code the watcher already has. pid is its own child (nohup execs setsid, which execs bash or, with --wait, returns the child's status), so make it `wait "$pid"; rc=$?` and exit with rc. Keep the status file only for people reading the log later, or fall back to it only when wait gives 127.
- **Clearing a policy's client limit in the console now keeps the old limit, and the console still says 'Settings saved'** (wbskt/Wbskt#1031, product). `Databases/Wbskt.Database/StoredProcedures/RegistrationPolicy_Update.sql:41; console src/app/features/workspace/policies/policy-tab/components/policy-settings-panel/policy-settings-form.service.ts:28 and policy-tab/services/policy-page.service.ts:260-263`  
  Policy 'porch' has a limit of 10. The user empties the Limit field and saves. PATCH {name, maxClients: null, autoApproval, isEnabled} returns 204, the toast says 'Settings saved', and the reload still shows 10. The cached-copy race from #956 also still happens: setEnabled (policy.service.ts:82-85) and the settings save both re-send cached fields, so one member's toggle or save puts back another member's limit or enabled state.  
  Fix: Ship Console#222: send removeMaxClients:true when the limit is cleared, send only the fields that changed, and have setEnabled send isEnabled alone. Update GEMINI.md's 'full replace' note at the same time. A contract change like this should wait for its only client in future.
- **The drain runs after the bus has stopped, so a step that sends a command or a notification during a deploy fails instead of being re-run** (wbskt/Wbskt#1008, architecture). `Hosts/Wbskt.Workflow.Engine.Host/Program.cs:116-117; Hosts/Wbskt.Workflow.Engine.Host/HostedServices/EngineLeadershipCoordinator.cs:92; Hosts/Wbskt.Workflow.Engine.Host/HostedServices/BranchExecutionPump.cs:71`  
  A deploy starts while a run is at, or reaches, 'Send to client: open the valve'. Before #1008 the step was cut short and the next leader ran it again. Now the publish hits a stopped bus, and the step fails with COMMAND_PUBLISH_ERROR. The run ends Failed and the valve never gets the command. A run that finishes in the same window never publishes RunCompleted, so the console never sees it end and a parent step waits for the orphan GC.  
  Fix: Keep the bus up until the pump has drained. Register the pump after the coordinator again, and start the drain on IHostApplicationLifetime.ApplicationStopping, which fires before any StopAsync, so no new node starts. If consumers must stop before the drain, stop only the receive endpoints first and stop the bus after the pump. Add a host-level test that publishes from a draining step.
- **After CredentialsRejectedException, the README's 'save the new secret and start again' (or 'clear and the next start registers') never works on the same WbsktClient** (wbskt/wbskt.dotnet#17, product). `wbskt.dotnet src/Wbskt/WbsktClient.cs:217-225 (with :94 and :488-496); README.md:129-143`  
  A hosted service catches CredentialsRejectedException from OnConnectFailed, writes the rotated secret with FileClientStorage.SaveCredentialsAsync (as the README shows) and calls StartAsync again -> login is sent with the old secret -> CredentialsRejectedException again, forever, until the process restarts. Same for ClearCredentialsAsync + StartAsync: it never registers.  
  Fix: On a final CredentialsRejectedException set `_resolvedRefId = _resolvedSecret = null` (credentials stay on disk) and invalidate the token cache, so the next StartAsync re-reads storage; add a test: reject, save new secret, StartAsync, connected.
- **A password attempt reserved but never settled stays counted, and enough of them refuse the account with no expiry** (wbskt/Wbskt#1051, senior). `Hosts/Wbskt.Auth.Host/Services/AccountCredentials.cs:52-70; Databases/Wbskt.Database.Auth/StoredProcedures/User_BeginPasswordCheck.sql:17-21`  
  An attacker posts 10 wrong-password sign-ins for victim@x and drops each connection while it is queued for a hash slot or before End runs. A SQL timeout or other fault between Begin and End does the same. Each reservation stays counted, so FailedLoginCount reaches 10 with LockedUntil NULL. From then on Begin refuses every attempt, including the owner's from a known browser and their re-entered password on change-password ('AUTH_ACCOUNT_LOCKED'). Nothing ever lapses: only a password reset or staff clears it. Before this PR a lock lasted LoginLockout and then lapsed.  
  Fix: Settle the reservation in a finally: a flag set once End has run, and if it has not, call EndPasswordCheckAsync(succeeded: true) with CancellationToken.None so the slot is given back. Or have User_BeginPasswordCheck turn a count at the limit with no LockedUntil into a lock (or a reset) instead of refusing forever.
- **Skipping a non-matching hold write leaves LastEventAt behind, so a late matching message starts a hold the newer reading already ended** (wbskt/Wbskt#1053, senior). `Hosts/Wbskt.Workflow.Engine.Host/InboundAdapters/ClientHoldStateCache.cs:35 with Databases/Wbskt.Database/StoredProcedures/ClientHoldState_Record.sql:37`  
  The hold trigger is 'temp > 30 for 60 s', the row is clear and the last write was at 09:59:59. The device sends 31 at 10:00:00, then 25 at 10:00:01. The engine handles 25 first: it is skipped as already clear, and LastEventAt stays 09:59:59. Then 31 arrives: 10:00:00 >= 09:59:59, so a hold starts. With no further reading inside 60 s, the ticker fires a run even though the newest reading did not match. Before #1053, 25 set LastEventAt to 10:00:01 and 31 was ignored.  
  Fix: Keep the newest event time per trigger in the cache with the clear flag, and raise it on a skipped message. Drop a matching message older than that without writing, or write it as a non-match. The simplest alternative is to skip only when the cached time is not older than @EventAt.
- **A closed tenant keeps its paid plan forever, so the staff overview counts deleted accounts as paying** (wbskt/Wbskt#1027, architecture). `Databases/Wbskt.Database.Auth/StoredProcedures/User_Delete.sql:176-180; Databases/Wbskt.Database.Auth/StoredProcedures/TenantSubscriptions_GetToReview.sql:24,36; wbskt.admin src/Wbskt.Admin.Host/Platform/AuthReader.cs:106-111`  
  A Pro subscriber deletes their account. AccountDeletionService cancels the Dodo subscription ('cancelled', which SubscriptionPlan.Decide treats as paid until period end) and User_Delete closes the tenant with PlanCode='Pro', PlanSource='Subscription'. The review job now skips it, so it never drops to Free. The staff overview's PayingAccounts and plan breakdown count it for good. Account search lists it as a 'Closed account' with a Pro plan and offers staff actions on it. A closed tenant on an open-ended staff plan is likewise counted under 'on a staff plan' forever.  
  Fix: In User_Delete, when closing, also set PlanCode = N'Free', PlanSource = N'Default', PlanEndsAt = NULL. Or filter `ClosedAt IS NULL` wherever [admin].Accounts is counted. File the admin-repo follow-up so it shows ClosedAt and refuses staff actions on a closed tenant.
